# RCA — whatsapp-crm-146 build failure (GitHub auto-triggered redeploy)

## Problem statement
A GitHub-auto-triggered redeploy failed with "Build › Build image: Failed to build an image."
Primary suspicion from the handoff: the backend `requirements.txt` pins
`reportlab==5.0.0`, `pymupdf==2.0`, `pymupdf4llm==2.0`, `pymupdf_layout==2.0`
do not exist on public PyPI and break the fresh image's `pip install`.

## What I could and could not inspect
- The **failed** GitHub-triggered run is NOT present in this deployment's run history
  (`describe_deployment_state.recent_runs` lists only terminal-success + the active run).
  Its run_id was not handed to me, so I had no handle to read its build logs.
- `get_build_logs` for the available (active, successful) run returns `build_lookup_limit`
  ("build lookup limit reached; run was not resolved") in both filtered and raw mode — so
  build-log access is not working for this deployment from my side right now.
- I therefore could NOT read the actual failing build step's log lines. Everything below is
  from reproducing the hypothesis in an isolated sandbox against the active run's source
  (same requirements.txt, since the handoff states the GitHub changes added no new deps).

## Evidence — the stated pip hypothesis is DISPROVEN
Sandbox (template `fastapi_react_mongo_shadcn_base_image`), pip resolving against public PyPI
(`--index-url https://pypi.org/simple`):

1. `pip index versions` confirms ALL four versions are published on public PyPI:
   - reportlab → `Available versions: 5.1.0, 5.0.1, 5.0.0, ...` (5.0.0 present)
   - pymupdf → `pymupdf (2.0)` present
   - pymupdf4llm → `pymupdf4llm (2.0)` present
   - pymupdf_layout → `pymupdf_layout (2.0)` present
2. A real install succeeds:
   `pip install reportlab==5.0.0 pymupdf==2.0 pymupdf4llm==2.0 pymupdf_layout==2.0`
   → `Successfully installed ... pymupdf-2.0 pymupdf4llm-2.0 pymupdf_layout-2.0 reportlab-5.0.0`
3. These exact pins are also what the CURRENTLY LIVE image (active run 3e796c52) was built from,
   so the file as written is demonstrably buildable.

Conclusion: these four pins resolve and install cleanly. They are NOT the cause of the build
failure. Do not downgrade/change them — that would be chasing the wrong lead.

## Side observation (not the failure, but noted)
When I forced the PUBLIC PyPI index on the full `requirements.txt`, the resolver stopped at
`emergentintegrations==0.2.0` → "No matching distribution found". This package is Emergent-
mirror-only and is expected to be served by the build's internal index (the live image built
fine with it). It is only a false failure of my forced-public-index test, not a build defect —
UNLESS the failed build somehow lost access to the Emergent pip mirror (an index/network
condition), which would surface as exactly this line. Worth checking in the real failed-build
log if it can be retrieved.

## Root cause
UNRESOLVED from direct logs. The specific hypothesis handed over (those 4 PDF pins missing on
PyPI) is positively refuted. The real failing step/error could not be read because the failed
run is not surfaced in run history and build-log lookup returns `build_lookup_limit`.

## Recommended next actions
1. Re-trigger the deploy and capture the exact `build_image` step error, OR provide the FAILED
   run_id so its Cloud Build log can be read. Given identical source already built successfully,
   a transient build-infra / pip-mirror reachability failure is a live possibility.
2. Do NOT modify reportlab/pymupdf/pymupdf4llm/pymupdf_layout pins — proven valid and installable.
3. If the real log shows `emergentintegrations==0.2.0` "No matching distribution", that points at
   the build's pip mirror/index access, not the app source — escalate as platform/build-infra.
