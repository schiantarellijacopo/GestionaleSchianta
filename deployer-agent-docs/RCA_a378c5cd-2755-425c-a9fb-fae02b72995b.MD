# RCA — Policy OCR imports doubled "imposte" (50.86 vs 25.43) in production

## Problem statement
`POST /api/utility/ocr-polizza` ("Riconoscimento polizza") imports `imposte = 50.86`
for policy 184643597 (CASTELANELLI FILIPPO, Cattolica, moto) in production, exactly 2× the
correct 25.43 (= lordo 250.00 − netto 205.43 − ssn 19.14 − diritti 0). Preview returns 25.43 for
the same PDF. Reporter suspected a stale backend image or stale frontend bundle.

## Verdict: NOT a build/deploy/cache problem. It is a source-code robustness bug + LLM non-determinism.

### 4. What production actually returns, and why a redeploy will NOT fix it
I could not invoke the live OCR endpoint (it needs a PDF upload + auth + an LLM call), so the
50.86 figure is your observation. I PROVED the deployed code produces exactly that on a plausible
extraction path, by running the deployed `_riconcilia_premi()` standalone in a sandbox:

- Case A — LLM reads `premio_lordo_totale`=250, netto=205.43, ssn=19.14 → **imposte = 25.43** ✅ (preview's lucky extraction)
- Case B — `premio_lordo_totale` NOT read, garanzie rows duplicated (imposte sum 50.86, netto sum 205.43) → **imposte = 50.86** ❌
- Case C — `premio_lordo_totale` NOT read, LLM already doubled `imposte_totali`=50.86, no garanzie detail → **imposte = 50.86** ❌

**Root cause:** The "deterministic" fix only engages on the branch
`if lordo_letto and netto is not None:` (line 220). The correct value 25.43 is derived **only when
the LLM returns `premio_lordo_totale` (the "totale da pagare")**. When the LLM omits/mis-reads that
field:
- it falls through to `elif len(imposte) >= 2: sum(imposte) − cf` — which sums duplicated garanzie
  rows → 50.86; or keeps the LLM's already-doubled `imposte_totali`.
- then line ~229 recomputes `premio_lordo_totale = netto + imposte + ssn + diritti = 275.43`.
- the final "Quadratura finale" guard (line 238) compares `netto + imposte + ssn + diritti` to that
  recomputed lordo — deviation is 0, well under the 0.50 threshold — so the guard does NOT correct
  it. The doubled value survives.

The OCR extractor is `.with_model("gemini", "gemini-3-flash-preview")` (ocr_polizza.py:143), a
non-deterministic LLM. Preview and prod run identical code; the difference is purely that preview's
OCR call read the `premio_lordo_totale` and prod's did not. So **re-running / redeploying from HEAD
will not reliably fix it** — HEAD's own code yields 50.86 whenever the lordo isn't read.

## Suggested fix (Code — E1 / main agent)
Make `_riconcilia_premi()` robust to a missing `premio_lordo_totale`, and/or make the final
quadratura guard not depend on a lordo it just recomputed from the suspect components:
- Prefer an **independently-read** `premio_lordo_totale` / "Totale da pagare" as the anchor; do not
  overwrite/recompute lordo from the garanzie before the quadratura check.
- De-duplicate garanzie rows before summing (the LLM duplicates rows → doubled imposte/netto).
- Add a sanity rule: if `imposte_totali` ≈ 2×(lordo − netto − ssn − diritti) or if garanzie contain
  duplicate (premio_netto, imposte) pairs, collapse them.
- Strengthen the OCR prompt to always return the document "Totale da pagare" / premio lordo, and
  consider a more deterministic model/temperature for extraction.
- Add a regression test for the no-lordo / duplicated-garanzie extraction so the residual path
  yields 25.43.

## Not involved
No DB migration, no secret change, no stale image, no build cache, no frontend/CDN issue. Default
URL healthy; this is a single-endpoint data-correctness bug driven by LLM extraction variance.
